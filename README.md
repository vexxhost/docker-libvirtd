# libvirtd image

This repository builds the libvirt/QEMU container used by Atmosphere.

## Windows SMBIOS compatibility

Windows booted with legacy BIOS/SeaBIOS can fail to discover SMBIOS 3.0
tables. This leaves fields such as the UUID in
`Get-CimInstance Win32_ComputerSystemProduct` empty. See
[QEMU issue 2008](https://gitlab.com/qemu-project/qemu/-/issues/2008).

The amd64 QEMU package `1:8.2.2+ds-0ubuntu1.18+vexxhost3` backports the
upstream automatic entry-point selection to QEMU 8.2. It tries SMBIOS 2.x
first and rebuilds with SMBIOS 3 if the table size or processor topology
cannot be represented by SMBIOS 2.x. The backport preserves QEMU 8.2's
legacy interfaces and restores user-provided blobs and counters before
retrying. It does not import the unrelated SMBIOS refactoring from QEMU 9.

There is an intentional downstream compatibility change: the default is
also changed for PC/Q35 8.1, 8.2, and Ubuntu noble/noble-v2 machine types.
Upstream QEMU 9 retains the old 64-bit default for 8.1/8.2, so copying the
upstream default change without addressing these machine types would leave
existing instances affected. Machine types 8.0 and older retain their
32-bit defaults. The machine name, CPU model, and configured UUID are not
changed by this patch.

Explicit QEMU machine properties still take precedence:

| Property | Behavior |
| --- | --- |
| `smbios-entry-point-type=auto` | Prefer SMBIOS 2.x; fall back to SMBIOS 3. |
| `smbios-entry-point-type=32` | Require SMBIOS 2.x; reject an unrepresentable configuration. |
| `smbios-entry-point-type=64` | Retain SMBIOS 3 behavior. |

These are QEMU command-line properties, not existing Atmosphere or Glance
settings. Do not add them as arbitrary image metadata or modify Nova's
database to apply them.

The default change also applies to UEFI guests using these machine types.
UEFI does not have this particular Windows discovery problem. Large
configurations that fall back to SMBIOS 3 can still encounter the Windows
bug when using SeaBIOS; `auto` does not remove the limits of SMBIOS 2.x.
Use a tested UEFI image for such new Windows guests.

### Validation

Every amd64 image build runs the following against the installed QEMU
binary, with networking disabled and TCG acceleration (no KVM required):

```sh
python3 hack/test-smbios.py -v
```

To test a locally built QEMU with separately installed firmware:

```sh
python3 hack/test-smbios.py \
  --qemu /path/to/qemu-system-x86_64 \
  --bios /path/to/bios.bin -v
```

The tests inspect the actual firmware tables for all affected versioned
machine names, older defaults, explicit overrides, UUID/identity preservation,
processor-topology fallback, and large-table fallback with user-provided
structures. They also boot SeaBIOS and check that it publishes a valid
32-bit entry point pointing to the expected identity. No guest OS image
or network connection is needed.

These tests do not replace Windows, UEFI, or migration qualification.
Before promoting the image for production, record results for:

- Windows Server 2019/2022 and a supported Windows client image: legacy BIOS
  and UEFI, i440fx and Q35, including the machine types already in use.
- `Get-CimInstance Win32_ComputerSystemProduct` identity before/after a hard
  reboot and a full stop/start; expected UUID, manufacturer, product, and serial.
- Linux BIOS/UEFI guests, including a configuration that requires SMBIOS 3.
- Live and cold migration between old and patched QEMU images in both
  supported directions, then a hard reboot/stop-start on the destination.
  Check identity, Windows activation, NIC/disk enumeration, and connectivity.

Run `hack/test-windows-smbios.ps1` inside each Windows guest before and after
those lifecycle actions, supplying the identity configured for that instance:

```powershell
.\test-windows-smbios.ps1 `
  -ExpectedUuid '<configured-instance-uuid>' `
  -ExpectedVendor '<configured-manufacturer>' `
  -ExpectedProduct '<configured-product>' `
  -ExpectedSerial '<configured-serial>'
```

It fails if CIM cannot return the identity or any value differs from the
expected identity. The script is a guest-side qualification check and is
not run by the Linux image build.

### Rollout

This change requires a planned compatibility rollout because it changes
the firmware tables generated by existing machine types. Deploying the
image or restarting libvirt alone does not replace running QEMU processes.

1. Inventory effective machine types and firmware modes. Capture the
   configured UUID and other identity fields before changing the images.
2. Qualify mixed-version migration before allowing movement between patched
   and unpatched computes. If it is not qualified, keep the pools separate
   during the rollout and schedule cold restarts onto patched computes.
3. Update the compute images and perform the validated hard-reboot or
   stop/start procedure for affected guests. Verify the guest identity again.
4. Backport the image fix to affected supported branches and update
   Atmosphere's pinned libvirt image digests with an upgrade note. The
   affected Atmosphere lines identified for follow-up are 5.x from 5.5.0,
   6.x, and 7.x; actual exposure depends on the deployed image and VM settings.

Retain the previous image digest for rollback. Returning to its firmware
behavior requires recreating the QEMU process through the tested procedure;
changing a container image alone is not a guest rollback. Avoid cloud-wide
machine-type downgrades as a workaround for this single firmware issue.
